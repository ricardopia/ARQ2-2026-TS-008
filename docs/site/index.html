TaskMaster: cómo resolvimos cada una de las 5 features

Un Kanban empresarial tipo Trello que sufría dos fallas silenciosas: Lost Update (A edita la descripción, B mueve la tarjeta con un payload viejo y borra el trabajo de A) y caída por RAM (un archivo de 150 MB pasa entero por la API Node.js). Esta página recorre el flujo de cada solución con demos interactivas que replican el comportamiento definido en el spec.md y en el código.

Falla 1 · Lost Update

Last-write-wins: el cliente de B reenvía toda la tarjeta cargada antes y pisa la descripción de A sin ningún error.

Falla 2 · Memoria agotada

El stream completo de 150 MB llega a la RAM del API, que desconecta a quienes solo querían leer tareas.

Arquitectura en una mirada

Cada feature mapea a contenedores concretos del diagrama C4 y a un ADR. El hilo común: PostgreSQL es la fuente de verdad y todo lo demás (caché, broker, notificaciones) se desacopla de la escritura.

Feature 1

Roles, workspaces y permisos de tablero

Dos niveles de rol, evaluados en cada request contra PostgreSQL (no viajan en el JWT, así un cambio de rol aplica de inmediato).

Problema

Clientes enterprise necesitan que unos solo lean, otros editen y otros administren, y que quien no pertenece ni siquiera sepa que el recurso existe.

Solución

  • WorkspaceRole: OWNER / MEMBER · BoardRole: ADMIN / EDITOR / VIEWER
  • El OWNER del workspace es ADMIN implícito de todos sus tableros.
  • Sin rol efectivo → 404 (no revela existencia); rol insuficiente → 403.
  • Hay que ser miembro del workspace antes de entrar a un tablero.

Feature 2

Resumen de tablero optimizado

Abrir un tablero no debe arrastrar el peso de todas las tareas: solo tarjetas livianas, servidas desde Redis.

Problema

Cada tarea puede tener hasta 20.000 caracteres de descripción más adjuntos. Un tablero de 1.000 tareas cargado completo es enorme y lento.

Solución

  • GET /boards/{id}/summary devuelve columnas + TaskCard (id, título, asignados, fecha, posición, versión).
  • La consulta usa select: TASK_CARD_COLUMNS: nunca lee description.
  • Caché board-summary:{id} en Redis, TTL 300 s; se borra tras cada escritura que cambia el resumen.
  • myRole se calcula por request y no se cachea. Si Redis cae, se sirve desde PostgreSQL.

Feature 3

Control de concurrencia optimista (OCC)

Es el corazón del caso. Cada tarea tiene un version entero que viaja como ETag; toda escritura debe confirmar con If-Match la versión que vio.

Problema

B reenvía el payload completo cargado antes y la API lo acepta: la descripción de A desaparece sin error (last-write-wins).

Solución (ADR 001)

  • Escritura atómica en SQL: UPDATE … WHERE id=$1 AND version=$2, correcto con N réplicas.
  • 0 filas afectadas → 412 VERSION_CONFLICT con la tarea actual. Sin If-Match → 428.
  • Escrituras parciales por intención: PATCH /tasks/{id} (contenido) y PATCH /tasks/{id}/position (mover). Mover nunca toca la descripción.
  • Rechaza campos desconocidos (400); no existe PUT.

Feature 4

Subida pesada fuera de la API

Los 150 MB nunca tocan Node.js: el navegador sube directo al storage con un POST pre-firmado y un worker procesa el archivo en segundo plano.

Problema

El stream completo entra por la API, llena la RAM y desconecta a todo el equipo.

Solución (ADR 002)

  • La API solo autoriza (EDITOR+), crea el adjunto PENDING y firma una política: clave, Content-Type y tamaño exacto, 15 min.
  • El gateway rechaza cuerpos > 1 MiB (413).
  • confirm verifica el objeto (HEAD) y encola el job vía outbox, idempotente (un solo job aunque confirmes dos veces).
  • El File Worker valida la firma del archivo, genera preview WebP (≤512 px) y cierra el estado. Reintentos 10 s / 60 s / 300 s y luego DLQ.

Feature 5

Notificaciones web de cambios en el tablero

Quien mira un tablero se entera de las modificaciones en segundos y ningún evento se pierde, aunque el broker falle justo después del commit.

Problema

Publicar directo al broker tras el commit pierde el evento si algo falla entre ambos pasos (dual-write). Además solo deben enterarse usuarios autorizados.

Solución (ADR 003)

  • Outbox transaccional: el evento se inserta en outbox_events en la misma transacción que el cambio.
  • El Outbox Relay publica a RabbitMQ con reintentos y backoff.
  • El Realtime Service abre WebSockets con un ticket de un solo uso (30 s, GETDEL en Redis), valida acceso al suscribirse y envía solo a suscriptores de ese boardId.
  • Entrega at-least-once: el cliente deduplica por eventId e ignora versiones viejas.
